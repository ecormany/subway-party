# Adding a new transit network

This is a checklist for adding a new transit system (e.g. "MTA Maryland", "TTC Toronto") to Subway Party. It's written for both humans and Claude/agents — follow it in order, since later steps depend on decisions made in earlier ones.

A new network touches up to four files:

1. `src/data/stations.ts` — the `systems` registry (id, display name, city, color, emoji)
2. `scripts/generate-stations-ts.mjs` — the **source of truth** for that same registry, plus (maybe) manual station entries
3. `scripts/scrape-wikipedia.mjs` — scraper config, if Wikipedia has a usable table for this system
4. `src/data/lines.ts` — how raw "line" text becomes colored line badges

Everything else (system filter buttons, browse/search, calendar, stats) is driven off `systems` and the `stations` array automatically — you don't need to touch `App.tsx` or `App.css`.

## Step 0: Decide how you'll get station data

Look up the system's Wikipedia "List of ... stations" article (e.g. `List_of_Washington_Metro_stations`).

- **Has a wikitable with Station / Line(s) / Opened columns?** → scrape it (Step 2).
- **No opening-date column, or dates buried in prose/individual station articles?** → enter stations manually (Step 2, "manual" path). MBTA, SEPTA, and RTA all work this way today — see the `manual` array in `scripts/generate-stations-ts.mjs`.

Either way you need, per station: **name**, **line(s)**, **opening date (YYYY-MM-DD)**, and ideally a **Wikipedia article slug** (for the station-card link and for coordinate lookup).

## Step 1: Register the system

Pick:
- `id` — short lowercase key, e.g. `wmata`, `cta`. Used everywhere as the system identifier.
- `name` — full display name, e.g. `"Washington Metro"`.
- `city` — used in the "station near {city}" Google Maps fallback search.
- `color` — one hex color representing the system as a whole (used for the active-filter button background).
- `emoji` — one emoji, ideally not already used by another system, shown next to the system name in filters and station cards.

Add the entry to the `systems` record in **both**:

- [`src/data/stations.ts`](../src/data/stations.ts) (what the running app currently imports)
- the copy embedded in the generated-file template inside [`scripts/generate-stations-ts.mjs`](../scripts/generate-stations-ts.mjs) (search for `export const systems`)

**These two must stay in sync.** `stations.ts` is fully regenerated by `generate-stations-ts.mjs`, so if you only edit `stations.ts` directly, your new system disappears the next time anyone reruns the data pipeline.

## Step 2: Get the station data

### Path A — scrapable Wikipedia table

Add a config object to the `SYSTEMS` array in [`scripts/scrape-wikipedia.mjs`](../scripts/scrape-wikipedia.mjs):

```js
{
  id: "wmata",
  article: "List_of_Washington_Metro_stations", // Wikipedia article title, underscores for spaces
  nameCol: "Station",   // substring match against the table's header row
  lineCol: "Lines",
  openedCol: "Opened",
  useTemplateLines: true, // only if lines are rendered as color-icon templates (e.g. {{Rint|...}})
                           // rather than plain text — see WMATA for an example
  linkLines: true,         // only if each line is its own link in the cell (lists or <br>-separated),
                           // which plain text would run together — see London Underground
  disambiguateByWiki: true, // only if distinct stations share a name; appends the article's
                            // parenthetical, e.g. "Edgware Road (Bakerloo line)"
}
```

Notes on the scraper:
- It reads every `table.wikitable` on the page and expands `rowspan`/`colspan` cells into a full grid, so merged cells (e.g. one "Line" cell spanning several station rows) work automatically.
- `nameCol`/`lineCol`/`openedCol` are matched case-insensitively as *substrings* of the header text — get the exact header wording from the live article if column detection fails.
- Rows whose "Opened" text contains "under construction", "planned", or "tbd" are dropped automatically (future stations).
- `parseDate()` handles "Month Day, Year", "Day Month Year", and bare-year formats. If a system's date format doesn't parse, either extend `parseDate()` or fall back to Path B for that system.
- The Wikipedia article link in the name cell becomes `wiki` (used for the article link and for coordinate lookup).
- The final dedupe is by `name+system`, so same-named stations are silently dropped unless you set `disambiguateByWiki`. Compare the `Found N stations` log line against the unique count you expect.

Run it and check the output looks right before wiring it into the generator:

```bash
node scripts/scrape-wikipedia.mjs > scripts/scraped-stations.json
```

The script logs (to stderr) which columns it found for each table — watch for `name=-1` or `opened=-1`, which means column detection failed.

### Path B — manual entries

Add station objects to the `manual` array in [`scripts/generate-stations-ts.mjs`](../scripts/generate-stations-ts.mjs), following the existing MBTA/SEPTA/RTA entries as a template:

```js
{ name: "Some Station", system: "wmata", line: "Red", opened: "1976-03-27", wiki: "Some_Station_(WMATA)" },
```

- `line` is free text — it just needs to be something [`lines.ts`](../src/data/lines.ts) (Step 3) can turn into badges.
- `wiki` should be the article slug (no leading `https://en.wikipedia.org/wiki/`) if one exists — it drives both the article link and the coordinate lookup.
- If a station is served by multiple lines and the system doesn't have per-route Wikipedia icons to scrape, decide now whether `line` should be a delimited string (comma or slash — see RTA's `"Red,Green,Blue,Waterfront"` or MBTA's `"Green/Red"`) and match that delimiter in your `lines.ts` handling in Step 3.

If a station complex needs to merge multiple physically-connected entries into one row (NYC does this — see `nycComplexes` in the same file), that pattern is NYC-specific; most new systems won't need it.

## Step 3: Teach `lines.ts` how to render badges

Open [`src/data/lines.ts`](../src/data/lines.ts) and add a case to the `getLineBadges()` switch for your new `system` id. Two common shapes:

**Simple color-named lines** (most systems — WMATA, CTA, BART, MBTA): define a color map and reuse the generic splitter.

```ts
const wmataLineColors: Record<string, { bg: string; fg: string }> = {
  Red: { bg: "#BF0D3E", fg: "#fff" },
  Orange: { bg: "#ED8B00", fg: "#fff" },
  // ...
};
```

```ts
case "wmata":
  return splitColorLines(lineStr, wmataLineColors);
```

`splitColorLines` scans `lineStr` for every known line name that appears as a substring and returns a badge per match, falling back to a single gray badge with the raw text if nothing matches. This means **your color-map keys must be exact substrings of what's in the `line` field** (check capitalization and whether "Line" is included).

**System needs custom logic** (irregular naming, badges that don't map 1:1 from raw text, station-specific overrides): write a small dedicated case, following the `septa`, `marta`, or `rta` cases as examples. `marta`, for instance, can't scrape color icons from its Wikipedia table, so it looks up a hand-maintained `martaStationLines` map by station name instead of parsing `line` at all. `rta` special-cases a two-tone "Waterfront" badge (`bg`/`bg2`) before falling through to the generic color splitter for the rest.

If you don't add a case, the `default` branch just shows the raw `line` string as one gray badge — functional but ugly. Do add a case.

## Step 4: Regenerate and verify the data file

```bash
node scripts/scrape-wikipedia.mjs > scripts/scraped-stations.json   # skip if Path B only
node scripts/generate-stations-ts.mjs > src/data/stations.ts
```

The generator also batch-fetches lat/lng coordinates from the Wikipedia API for every station with a `wiki` slug (rate-limited, ~1.5s between batches of 25 — expect this to take a while for a large system). Check its stderr summary line (`Fetched coordinates for N of M stations`) — a low hit rate usually means slug mismatches (redirects, disambiguation suffixes).

Diff the result before committing:

```bash
git diff src/data/stations.ts
```

Sanity-check:
- Your new system's stations appear, sorted alphabetically within the system.
- No duplicate `name+system` pairs (the scraper dedupes automatically; manual entries don't).
- Opening dates are `YYYY-MM-DD` and look plausible.

## Step 5: Verify in the app

```bash
npm run dev
```

Open the app and check:
- **Today / Browse**: your system's filter button appears with the right emoji, name, and active-state color.
- Selecting it shows the right line-filter chips with correct colors (this is where a `lines.ts` mistake usually shows up as a gray "unknown line" badge).
- A few station cards render sensible line badges, opening dates, ages, and working Wikipedia/Maps links.
- **Calendar**: pick a date you know has an opening in the new system and confirm it shows up.
- No new React key-collision warnings in the console (usually caused by duplicate `name+system` pairs — see Step 4).

`npm run build` (runs `tsc -b` then `vite build`) is a good final check for type errors.

## Step 6: Update the README

Add a line to the "Systems covered" list in [`README.md`](../README.md), matching the existing format (station count, "since" year). If you added scraper config, mention the system in the "Refreshing station data" section's list of scraped systems; if manual, add a note like the existing MBTA/SEPTA/RTA one explaining why.

## Checklist

- [ ] `systems` entry added in `src/data/stations.ts` **and** `scripts/generate-stations-ts.mjs` (identical)
- [ ] Scraper config added to `scripts/scrape-wikipedia.mjs`, **or** manual station entries added to `generate-stations-ts.mjs`
- [ ] `getLineBadges()` case added in `src/data/lines.ts`
- [ ] Regenerated `src/data/stations.ts` and reviewed the diff
- [ ] Verified filters, badges, calendar, and links in the running app
- [ ] `npm run build` passes
- [ ] README's "Systems covered" (and "Refreshing station data" if scraped) updated
